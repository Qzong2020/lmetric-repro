# 单卡 yaullm 适配建议评审与执行顺序

日期：2026-10-23（北京时间）。

对应用户本轮粘贴的“补丁解耦与运行时探针”建议；结合已完成的源码审计整理。本文记录判断、修订和待办，不代表单卡模型服务或反馈适配已经跑通。本轮只读取源码并整理文档，没有占用NPU、安装引擎或改动调度评分。

## 结论

建议的总体顺序有道理：先弄清作者补丁和Rust端协议，再用真实单卡探针确认当前引擎的实际行为，最后做最小迁移与逐步对账。当前应集中解决这条链路，不宜先启动多策略性能矩阵。

但原文中的“Host埋点直接平移”“零开销”“固定几步完成”“五项通过即100%完备”均不成立。当前最大的工作是保留跨进程、分块prefill、缓存与请求生命周期的联合语义；Python文件能改，不等于可以机械搬运。

最先要做的三件事中，作者补丁导出已经完成；Rust协议语法已查明，字段语义仍需逐项核验；真实模型运行时探针尚未执行。

## 3. Rust兼容协议：语法、语义和诊断分别验收

语法来源：[vllm_http.rs](/root/lmetric-repro/blitz-router/router/src/engine/vllm_http.rs:153)。实际消费来源：[colocation.rs](/root/lmetric-repro/blitz-router/router/src/engine/colocation.rs:455)。

### 顶层VllmMetric字段

| JSON字段 | 当前Rust类型 | 核验重点 |
|---|---|---|
| `prefill_tokens` | `usize` | 作者口径、当前步与命中修正的联合效果 |
| `prefill_token_budget` | `usize` | 原协议预算定义，不凭字段名填任意剩余预算 |
| `latency` | `u64` | 作者SSE为整数毫秒；不可误发秒或纳秒 |
| `outputs` | `Vec<VllmRequestStatus>` | 无token步可能为空，但其余状态仍需到达 |
| `new_block_hashes` | `Vec<BackendBlockHash>` | 哈希字宽、拆分顺序与编译feature |
| `evicted_block_hashes` | `Vec<BackendBlockHash>` | 对应旧内容，事件发生时点与顺序 |
| `evicted_block_ids` | `Vec<u64>` | 覆写前的物理块，避免新旧ID混用 |
| `cur_used_block_ids` | `IntMap<u64, Vec<u64>>` | 按request ID维护；增量语义与累计列表区分 |
| `new_block_hashes_ids` | `IntMap<u64, Vec<u64>>` | 与新完整块的对应关系，不按名字推断 |
| `op_exec_log` | `Option<String>` | 兼容字段；是否启用由所测路径决定 |
| `preempted_ids` | `Vec<u64>` | 抢占与恢复、缓存保留或重算 |
| `aborted_requests` | `Vec<u64>` | 主动取消、断联、异常的区别 |
| `step_id` | `u64` | 顺序、重启、空步；不能仅检查“有这个字段” |

`BackendBlockHash`依Rust编译feature为`[u64; 1]`或`[u64; 4]`；不是可随意替换的单个整数。IntMap的JSON对象key是十进制字符串形式的请求ID；确保所有ID和哈希均无截断、溢出或浮点损失。

### outputs中逐请求字段

| JSON字段 | 当前Rust类型 | 核验重点 |
|---|---|---|
| `request_id` | `u64` | HTTP外部ID与内部引擎ID映射 |
| `new_token_ids` | `Vec<u32>` | 真实增量token，不重复拼接 |
| `state` | `String` | 消费者当前识别`PREFILL`/`DECODE`；不是任意生命周期枚举 |
| `is_finished` | `bool` | 与取消/抢占事件去重，结束只结算一次 |
| `hit_token_cnt` | `u64` | 权威实际命中数，当前消费者要求与块大小对齐 |
| `prev_computed_tokens` | `u32` | 作者定义的步开始前计算进度；其他策略/预测路径可能使用 |

多数字段有Serde默认值，缺失时可能变成0、空数组或默认`DECODE`。所以“JSON反序列化成功”不表示引擎提供了有效状态。验收器应独立检查必需字段存在、取值和事件完整性。

原文提出的`Admitted`、`Scheduled`、队列快照、父哈希、引擎时间戳不全是上述现有协议字段。可放入独立审计记录或版本化扩展；对外必须转换成现有消费者真正理解的格式，不能假设Rust已经支持这些事件。

## 4. 不能直接照抄的状态与缓存计算

### 4.1 waiting/running与PREFILL

作者scheduler在有逐请求输出、且`num_computed_tokens == num_prompt_tokens`时生成`PREFILL`；通常对应prefill完成和首个输出。部分prefill步可能没有逐请求输出，靠空输出的step消息传递进度。

Rust在`PREFILL`事件上减少waiting。因此作者协议的waiting不能直接等于V1的`len(self.waiting)`，`bs-waiting`也不能直接等于V1内部running列表长度。两组指标都可以记录，必须命名区分并建立映射。

### 4.2 本步prefill量

在单KV组、纯文本、无speculation及同步执行的原型中，可用下式核对计划中的prompt计算量：

```text
prompt_work = min(max(prompt_length - computed_before, 0), scheduled_tokens)
```

这只是按调度前快照计算的参考量。实际完成、抢占/重算、命中跳过与非prompt token仍需分别记账；不能在异步完成时随手读一个已被后续步改写的`num_computed_tokens`。

作者首次调度的`prefill_tokens`累计包含`num_new_tokens + num_computed_tokens`，Rust另做命中修正，因此不能把上式值直接塞入同名旧字段就认定兼容。先写逐步账本，再核验跨端累计结果。

### 4.3 缓存新增、释放、驱逐

- 完整可复用块建立索引后报告新增；区分占位分配、计划提交和可安全复用的内容，保持引擎原有时序约束。
- `free_blocks()`使引用归零，不表示内容失效；随后仍可能命中。
- 真正移除旧缓存映射/复用物理块时报告驱逐；缓存reset另行报告。
- 不同物理块可能持有同一内容。删除一个副本不一定使该内容在实例中完全不存在，需要正确引用或多重映射。
- 解码会将原先未满的尾块填满；不能只根据输入长度推算整个请求的BlockStored总数。

现有vLLM已有原生KV事件，优先复用正确观测位置并补充缺失物理ID。不能额外调用破坏性`take_events()`，导致原生发布器或其他消费者丢数据。

### 4.4 哈希和完整命中边界

当前安装版`PrefixCachingHashAlgo`列出`sha256`、`sha256_cbor`、`xxhash`、`xxhash_cbor`；不能照抄原文的`builtin`选项。Rust本地token链使用`xxh3_64_with_seed`；同叫xxhash也不证明与Python引擎的哈希、序列化和seed一致。

需明确采用“跨语言相同哈希”还是“请求token/块偏移+物理ID映射”路径，并给固定向量与新增/删除测试。不能临时以dummy哈希伪造兼容。

当前引擎在全部prompt可命中时仍需要重算末token，块对齐可能使整末块重算。因此“缓存中保存了完整64-token前缀”不必等于“再次请求同一64-token输入时actual cached_tokens=64”。需要按真实命中上限建参考模型。[官方说明](https://docs.vllm.ai/en/latest/api/vllm/v1/core/kv_cache_manager/)

## 5. 首次运行时探针：先核实，再确定启动命令

探针优先使用本地Qwen2.5-7B，只占一张卡。模型用于适配验证，不替代正式Qwen2-7B性能实验。首次预检的8K上下文上限不用于验证完整长轨迹。

先核实以下项目，不直接执行粘贴内容中的固定启动命令：

1. **卡映射**：本容器可见物理3/6、框架逻辑0/1；验证单进程设备屏蔽后的实际映射，不盲目认定环境变量数字就是同一编号。
2. **实际类**：在EngineCore进程记录Scheduler、KVCacheManager、BlockPool的最终类、模块、源码位置和继承关系；必要时检查关键方法是否被插件替换。只import默认Scheduler不能证明运行时使用它。
3. **实际配置**：记录生效的block size、hash block size、哈希算法、KV group、cache dtype、cache容量、最大上下文、prefill预算、并发上限、async scheduling、eager/graph模式。
4. **开关独立性**：显式关闭异步并确认最终值；`--enforce-eager`不负责关闭async，没传`--async-scheduling`也不保证它为false。具体CLI负向开关先按当前版本帮助/解析器核实。
5. **普通生成**：验证固定token IDs可送入、输出长度可锁定、外部request ID可追踪；保存最终SamplingParams及实际输出计数。
6. **运行记录**：记录加载、初始化、计算和退出的耗时/显存，冷启动不计性能结果；退出后释放设备。

如果插件使用了自定义调度器，先判断是必要的硬件路径还是可关闭的可选优化，不能一概当作“劫持”或强行替换成不兼容基类。

## 6. 最小实现边界

沿作者已有链路迁移：

```text
缓存与调度观测
  → SchedulerOutput / EngineCore输出
  → msgspec序列化和ZMQ
  → core_client接收与过滤
  → AsyncLLM指标分发
  → /v1/metrics SSE
  → Rust反序列化与状态应用
```

建议分成三份可独立验证的改动：

1. 引擎观测与有类型IPC结构：不改评分、引擎选择和缓存替换策略；IPC字段按新旧schema和构造调用一起核查。
2. 前端SSE与请求ID适配：保留兼容输出，将诊断扩展与原字段分开。
3. 独立验收与离线重放：不复用生产端同一套计算函数充当“独立参考”。

特别注意：

- **不是仅四个文件**。需检查scheduler/output、缓存管理、EngineCoreOutputs、core、core_client、async_llm及服务入口等完整路径；具体文件名在版本间也可能变化。
- **空token消息不得丢失**。core返回了消息仍不够；IPC接收循环和前端输出过滤也必须放行。作者旧代码存在`outputs.outputs or outputs.scheduler_stats`过滤，需要核验仅缓存变化/重置的消息能否通过。
- **request ID透传是实质改动**。作者completion补丁去除了`cmpl-`前缀和`-i`子请求后缀；Rust要求u64。当前引擎内部重写ID时，应维护双向映射而非无条件删前后缀，限定首轮单prompt、n=1并测试取消路由。
- **序号分层**。每个引擎保留epoch与事件序号；调度step和空闲reset/abort等控制事件区分。一次step可能没有模型输出，多前端输出也不应被错算成多次前向。
- **队列和连接**。定义启动握手、积压上限、断连、慢消费者和重连恢复。不能无界积压，也不能静默drop；丢事件后必须显式失效并重置/同步状态。初版可限定唯一router订阅者，诊断使用另一路副本记录。
- **有开销且需测量**。复用IPC可以避免新增一条主通信路径，但采集、编码、拷贝、排队和SSE解析都可能增加开销。事件时间戳与公共单调时钟需统一，不能直接相减Python单调值与Rust Instant。
- **图/异步需要重验**。图模式可能改变profiling、默认配置与Host时序，不能假设仅替换execute_model就保证所有事件不变。

## 7. 重写单卡验收：保留目标，取消错误的固定断言

所有测试使用固定token向量、固定输出目标、n=1；显式检查采样和停止参数。基准/诊断侧记录engine truth、IPC/SSE和router applied三份记录。

| 测试 | 原建议的问题 | 修订后的通过条件 |
|---|---|---|
| A. 冷启动与请求生命周期 | 原协议没有Admitted/Scheduled两种直接事件；输入64、输出16不应在任意执行模式下强制解释成固定15个decode step | 从清空状态开始，观察请求ID进入、prefill完成、token增量及最终结束；事件只结算一次；总输出16；同步受限模式下另核对执行步；排空后活动/等待/prefill归零 |
| B. 共享前缀与尾块 | 90-token输入在prompt阶段只有1个新满块，但随后解码能继续填满尾块；随机生成内容也可能与后续测试碰巧共享 | 固定不与已生成后缀混淆的token向量；在无驱逐条件下验证90-token输入对前64-token前缀的命中；分开检查prefill阶段与decode阶段新增；对尾块填满时点做账 |
| C. 完整prompt复用 | 原建议遗漏末token/末块重算 | 单独重发完全相同且长度块对齐的prompt，记录最大可命中长度并按实际引擎规则对齐，不能把合法重算误报成缓存错误 |
| D. Chunked prefill | 两个600-token请求共享每步256的预算，不能要求每个请求必然256+256+88三步完成 | 先用一个无缓存请求验证分块，再加两个并发；按请求累加实际prompt工作，冷缓存无重算时为600；每步全batch预算不超限；记录实际拆分，不固定步数 |
| E. 驱逐与物理ID复用 | 64块×16只是名义1024 token；还需null/reserved块及生成余量，不能保证前两请求正好填满；过大max-model-len可能启动即失败 | 先从启动生效容量扣除保留与请求运行余量；使单请求可执行，再顺序加载独特前缀，累计工作集超过容量；验证旧hash删除、同ID新内容建立及后续命中与当前缓存账本一致，不要求某个指定请求必为0命中 |
| F. 取消与异常 | 客户端断流与显式abort不同；1–2步响应不是通用保证；预取/网络延迟也影响观察 | 分开测显式取消和真实HTTP断流；确认请求最终移除、仅结算一次，测量取消传播延迟，设置按实测制定的合理超时；随后请求可继续执行 |
| G. 排空与缓存reset | 排空不等于缓存清零 | 先验证完成后缓存仍可复用；再显式reset两端并验证缓存失效和随后冷命中，不接受只清Rust树或只清引擎 |
| H. 连接与反馈新鲜度 | 原五项未覆盖丢消息、重启、慢消费与反馈延迟 | 测SSE握手、空闲消息、序号缺口/重复、epoch变化、队列积压、断线失效及恢复；记录生成→应用→决策使用的事件年龄和资源开销 |

### 关于“预测命中必须100%等于实际”的修订

在固定且静止的缓存快照中，预期匹配应可精确验证。但在并发执行中，路由决策到引擎实际接纳之间可能发生缓存驱逐或新增；同一prompt的末块也可能因引擎取logits而重算。预测与实际不同不自动表示实现错误，作者本来就有命中反馈修正机制。

因此验收应是：

1. 静态已知条件下，按真实命中规则精确匹配。
2. 动态场景保留决策快照、事件序号和引擎接纳时间，能解释差异。
3. 真实命中反馈修正后，prefill账本和缓存状态在同一逻辑时点对齐。
4. 明确记录路由已接纳但尚未到达引擎的请求，不将跨时点差异直接判错。

不是强制50条随机请求的预测值无条件逐条相等，更不是因此绕过驱逐或修改策略。
