## 复现目标与设备部署

第一目标是两卡、两个独立服务副本的硬件迁移实验：同一真实请求流下，检查LMetric相对负载基线的TTFT、TPOT、吞吐和排队表现。原论文使用H20及更大集群；本实验属于缩小规模的NPU复现，不能承诺复现原文百分比或证明16卡扩展性。[论文实验设置](https://arxiv.org/html/2603.15202v3#S4.SS1)

部署为：`固定轨迹回放 → CPU上的blitz-router → 单卡模型副本A / 单卡模型副本B`。每个副本TP=1，先做prefill/decode共置。两卡一起TP=2只会得到一个模型实例，不适合第一阶段评估跨副本路由。双卡HCCL虽已通过，TP=1的两个独立副本不依赖跨副本张量通信。

优先正式模型为论文中的Qwen2-7B，使用与已有tokenizer一致的固定revision `453ed1575b739b5b03ce3758b23befdb0967f40e`（取自已归档的 `configs/paper_cpu/inputs.json`）。本地目前找到的是Qwen2.5-3B/7B/14B及Qwen3-30B-A3B，不是同一模型。Qwen2.5-7B优先用于接口及容量启动预检，但不能把其结果列为论文同模型结果。正式Qwen2-7B权重仍需准备，并锁定文件清单与校验和。

7B BF16权重约14GB量级，预计可在每张64GB卡上放置独立副本，实际KV容量和上下文上限需在服务启动后确定。先不引入量化，以免增加一个实验变量。Qwen3-30B-A3B的BF16权重约60GB量级，单卡KV余量紧，TP=2又失去第二副本；因此它不作为两卡首个模型，后续依据实测内存另行评估。

## 阶段与验收门槛

### 0. 固定版本与实验口径（约半天，估计）

在独立目录准备固定提交的干净源码，保留当前工作区与历史结果。本轮不继续改当前算法。

对齐router、request-sim、模型、tokenizer、原始轨迹、NPU引擎及作者配置的版本。作者编排仓库固定为 `MetricsTestRunner@3ad55e81923f8f33044aa68dc178858c6694971e`；本轮已归档README、根目录、完整文件树及两个示例配置。示例中的`new_clients.toml`是Azure轨迹，不能只因文件名“new_clients”就将它当作Qwen实验配置；必须追踪具体论文场景。

基线版本差异单列处理：

- 当前作者提交 `a005ceb` 原版策略为 `4*waiting + bs`。
- 论文图6(a)及较早实现为 `4Q+R`；按本地字段定义等价于 `3*waiting+bs`。
- 当前工作区已经被先前测试改成后者。正式实验不能把它混称为未经修改的作者版本。保留原版，若采用论文公式版本则独立命名、独立补丁和独立结果；仍未确认论文各图真正使用的实验提交。

验收：形成完整版本清单、基线定义和配置映射；每项改动能区分硬件适配、观测和策略变化。

### 1. 单卡真实推理（约半天至一天，估计）

先用本地Qwen2.5-7B验证服务加载、短请求与流式输出，再准备正式Qwen2-7B。依次在两卡验证；启动前确认物理卡3/6和框架逻辑卡0/1的进程屏蔽映射，避免两个副本误用同一卡。

初始使用eager、小并发和受限KV预算排查正确性。然后单独启用前缀缓存、chunked prefill及拟用于正式实验的执行模式，确认这些组合确实可运行。缓存块大小以引擎启动后实际配置为准：本地router和原始轨迹当前以16-token块为基础，若Ascend实际要求不同块大小，必须让token重建、哈希链、引擎与router统一，禁止仅改CLI冒充完成适配。

验收：两卡各完成一组短/长输入与不同输出长度的真实生成；能读取权威token数、无OOM/崩溃；重复前缀的实际命中行为可解释。启动预检耗时不用于正式策略对比。

### 2. 迁移作者的引擎状态反馈（最高优先级，工期待单卡原型后重估）

当前router通过 `/v1/completions` 发送token IDs，通过作者扩展的 `/v1/metrics` SSE维护每步执行状态与缓存。标准OpenAI响应和普通Prometheus指标不能替代这个反馈。作者[yaullm说明](https://github.com/blitz-serving/yaullm/blob/aa897f04a5a891c39e96ca2d554cf310d2933fa2/README.md)明确描述了该扩展。

本轮查到作者yaullm默认分支固定提交 `aa897f04a5a891c39e96ca2d554cf310d2933fa2`，其构建配置要求PyTorch 2.7.1；当前Ascend环境为PyTorch 2.10/vLLM 0.23。不能直接覆盖安装作者旧引擎。

首选方案是在隔离的当前Ascend引擎源码副本中移植最小观测接口，保持路由评分不变。先追踪作者补丁边界，再逐项迁移：

1. 请求ID、接纳/开始执行/结束/中止/抢占的生命周期事件。
2. 每步prefill工作量与真实cache-hit token计数。
3. 缓存块新增、物理ID复用、驱逐及请求占用块；明确哈希链与部分块语义。
4. 有序step ID、事件传输与最终输出，兼容当前异步执行路径。

如果无法直接移植SSE，可在引擎侧增加等价事件适配层，但必须保留真实调度和缓存语义。所有策略使用相同观测配置，并测量观测开销。

验收门槛：执行“重复前缀→并发→请求完成→受控内存压力触发驱逐→再次访问”序列；router预测与真实命中可逐请求核对；bs/waiting/prefill计数不负溢出，排空后回零；断流与失败可识别。此门槛未过，不启动正式策略性能比较。

### 3. 两副本闭环与指标链路（约半天至一天，估计）

两张卡各加载同一正式模型，CPU router用release构建。先用几十至几百请求验证闭环，再增加压力。统一引擎参数、上下文、缓存容量、并发上限和输出限制。

复用同一份离线重建的token输入；作者inflater会随机生成文本，不能为各策略重新随机生成。每个策略使用相同请求ID、到达时间和生成token数；不重复应用chat template。

将已有独立CPU统计模块接入真实观测路径，逐字段比对作者指标脚本：记录发送、首/末内容到达、完成、权威token计数及失败。TTFT与TPOT既记录定义也记录测量来源；不能以SSE chunk数当token数，也不能用DONE时间延长解码区间。保留每请求原始记录和CDF，记录路由等待/后端等待，以解释收益来源。

验收：统一时钟记录core→前端→Rust应用及路由决策使用的状态年龄，监控SSE积压、CPU节流和Host下发；两实例都接到请求；缓存局部性与负载状态真实反馈；成功、失败、超时请求总数可对账；整个负载窗口按预定时间发出，没有被8核CPU发压瓶颈悄悄降速。

### 4. 最小有效性能对照（状态对账及新鲜度验收通过后，约2–4小时机时起）

先固定一个公开轨迹的连续时间窗口，重放真实到达间隔和输入/输出长度。首轮可用2分钟同源预热+5分钟测量，但不能只截取最有利的稳定区间；起止位置、数据哈希及保留比例必须记录。

先做LMetric与明确版本的vLLM负载基线；round-robin作为附加控制。针对同一固定参照配置校准系统容量，选中低和接近饱和的两个负载点，所有策略使用同一到达序列和缩放因子。禁止按每个策略自身能力重新调整负载。每组至少3次重复，交错执行次序；排空后显式重置两端缓存并验证，建立相同冷起点，再由各策略运行同源预热。热缓存分布允许由策略形成，不声称预热后物理缓存相同；预热不计入统计。

先用诊断轮记录自然缓存容量、实际驱逐、工作集与同快照策略分歧率，再预先声明容量/负载扫描；不以固定5%分歧或40%–70%容量当普适门槛，不筛选有利窗口。首轮3策略×2负载×3重复=18组；按每组7分钟约2.1小时，另加启动、排空、校准、失败重跑时间。这是机时估计，不包含接口移植。

输出：TTFT、TPOT的逐请求CDF及P50/P95/P99；完成吞吐、token吞吐、错误/超时率、两副本负载与缓存命中。吞吐点明是到达窗口还是包含排空的完成窗口，长请求必须排空或明确标为未完成。报告重复波动，不预设LMetric一定胜出；也不能只报告TTFT获益而省略TPOT退化。

### 5. 扩展复现（首轮结果可信后）

扩展到TraceA/TraceB、更长窗口和3个负载点，再逐项加入Bailian、Dynamo、预测式llm-d以及论文热点保护。完整3策略×2轨迹×3负载×3重复为54组；若每组2分钟预热+10分钟测量，则仅请求窗口就约10.8小时，更多基线会继续增加。

预测式基线的性能模型须在NPU上重新采样，不能沿用H20预测网格。热点保护应与基础LMetric分开报告，再做消融；公开场景不足以覆盖论文私有轨迹或线上部署时，要明确缺失。最终判断是“两卡NPU上能否复现性能趋势及机制”，与原硬件逐数值复现区分。

## 主要困难与处理方式

| 困难 | 当前证据/影响 | 处理与停止条件 |
|---|---|---|
| 引擎接口/版本代差 | 作者yaullm要求旧Torch；现有Ascend引擎缺少已查路径中的作者事件字段，不能直接接router | 隔离迁移最小补丁；生命周期和cache事件未验证前停止性能对比 |
| 两卡规模 | 可以形成两个独立副本，但无法代表原H20集群规模 | 单卡一副本；研究趋势，不套用论文收益百分比 |
| 模型差异 | 当前只有Qwen2.5等本地权重，Qwen2-7B正式权重未准备 | 先本地Qwen2.5-7B预检，正式锁定论文模型及revision |
| 缓存块/事件语义 | router默认16，Ascend实际后端可能调整；异步事件与块复用易造成虚假命中 | 读取实际配置并统一块与哈希；真实驱逐与状态对账 |
| 长请求 | TraceA最大输入89,286 tokens；TraceB最大66,446 | 固定Qwen2-7B配置上限131072；须核查作者实际启动参数与轨迹处理，并验证长请求在NPU实际可用性；不自行发明正式过滤规则 |
| CPU/主存瓶颈 | 8核/64GiB，要同时负担两引擎、tokenizer、router与回放 | 提前离线重建、release router、记录发出延迟；CPU限制先调进程与配置，再考虑独立发压机 |
| 参数与编译 | 图捕获、batch预算、KV容量会显著改变延迟 | 先eager正确性，再固定正式执行模式，所有策略一致，记录启动实际值 |
| 基线版本争议 | 已确认当前提交与历史公式不同，未确认论文实验版本 | 维护明确命名的原版与论文公式对照，不无声覆盖作者实现 |
| 不利结果 | NPU计算比例或两副本规模可能改变调度收益 | 查队列与缓存证据；如无收益或有退化如实报告，不反向调参挑结果 |

排障时记录“出现在哪一阶段→原始错误/指标→对结论的影响→尝试过的处理→是否还能继续”。影响结果口径的版本、过滤或策略变化先单列说明，不能只给“跑通了”的结论。

第一阶段预计核心闭环需数个工作日，最大不确定性是状态反馈移植；上述为工作量区间，不是完成承诺。本轮没有开始模型下载、引擎迁移或正式发压。
